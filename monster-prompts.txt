Project: "Monster", a Stunts-style monster truck game in C++17 compiled to
WebAssembly, deployed on GitHub Pages. The project is attached as monster.zip
(unpack it into a working directory before starting).

Layout:
  src/Math.h        Vec3, Quat, Mat4
  src/Check.h       require(), throws natively and traps in wasm
  src/Track.*       circuit centreline: a cursor walk of straights, arcs, a
                    bridge profile and a loop. 506 PathPoints over 988 m.
                    PathPoint has position, forward, cross, normal, Kind
                    (Flat, Embankment, Bridge, Loop), corner flag, distance.
  src/Terrain.*     collision world. Face quads with a Surface enum, a uniform
                    grid over the solid triangles, and
                    raycast(origin, direction, reach, Hit&). Also the crushable
                    wreck. The ground is a half-space at y = 0.
  src/Truck.*       rigid body, four ray-cast sprung wheels, tyres, air control.
                    Body frame: x forward, y up, z right.
  src/Judge.*       air time, flips, landing rating.
  src/Game.*        fixed 240 Hz step loop, score, laps, HUD string.
  src/Mesh.*        flat-shaded triangle soup, 6 floats per vertex (xyz rgb),
                    lighting baked into the vertex colour.
  src/Scene.*       ChaseCamera and the per-frame scene mesh builder.
  src/wasm_api.cpp  C functions exported to JavaScript.
  docs/             the published site: index.html, monster.js (WebGL + input),
                    and the committed monster.wasm.
  tests/            test_game.cpp (native), Autopilot.* (a driver that completes
                    a clean lap, used by the tests), smoke.mjs (drives the wasm
                    build in Node).

Build and test:
  make test                        native tests, any C++17 compiler
  make wasm WASI_SDK=/path/to/sdk  builds docs/monster.wasm (WASI SDK 25)
  node tests/smoke.mjs             drives the wasm build
  make serve                       local server on http://localhost:8000

Current wasm exports: monster_init, monster_reset, monster_recover,
monster_set_controls, monster_step, monster_render, monster_vertices,
monster_view_projection, monster_hud.
The HUD string is pipe separated: "speed|score|best|message|lap|lap time|best lap time".

House rules for every change:
- Use the "mycodestyle" skill for all C++ you write.
- make test, make wasm and node tests/smoke.mjs must all pass when you are done.
- Do not break existing tests. If a test needs to change, say why.
- Add tests for what you add. Prefer tests that assert behaviour over tests that
  assert constants.
- No test-only hooks in production classes. If a test needs a capability, add it
  as a feature the game could legitimately use, or test at a lower level.
- Verify visual changes by driving the real page in headless Chrome and looking
  at the screenshots, not only by reasoning about the code.
- Keep the flat-shaded look: no textures, no asset files, geometry stays
  procedural.

Add visible checkpoints to Monster: five gates spaced around the circuit, each
two poles carrying a banner with its number on it. A lap only counts if every
checkpoint was passed, in order, during that lap.

What already exists, and should be kept rather than replaced:
Game::updateProgress() already enforces ordered gates. It advances m_progress
through the 506 centreline points using m_gateRadius (12 m) and m_gateWindow
(10 points), and a lap is only credited when progress reaches the last point.
That is why the loop and the bridge cannot be skipped today. Build the
checkpoints as a coarse, visible layer on top of this, do not remove it.

Work:

1. Track: choose five checkpoint positions, roughly evenly spaced by distance
   along the centreline, and expose them as track point indices
   (getCheckpoints()). Place them on Flat road only, never inside the loop, on
   the bridge deck, or in a bend. Checkpoint 1 should be at or just after the
   start line.

2. Game: record which checkpoints have been passed in the current lap. A lap is
   credited only when all five were passed; otherwise crossing the start line
   does not increment the lap counter and does not record a lap time. Clear the
   record at the start of each lap and on reset(). Expose how many have been
   passed so the HUD can show it.

3. Game: add "void startAt(size_t pointIndex)", which places the truck upright
   on the centreline at that point, at rest, and sets progress accordingly.
   This is a real feature (restarting from a checkpoint later) and it also lets
   the tests start a lap partway round.

4. Scene: draw each gate as two vertical poles just outside the road edge, with
   a banner spanning between them above the road, high enough to drive under.
   Put the checkpoint number on the banner. Build the digits from quads
   (seven-segment style is fine and suits the look). Gates are static geometry.

5. HUD: add a checkpoint field, for example "CP 3/5". The HUD string format
   changes, so update docs/monster.js and tests/smoke.mjs to match.

Tests to add in tests/test_game.cpp:
- A full autopilot lap passes all five checkpoints and the lap is credited.
- A lap started partway round with startAt(), so that early checkpoints are
  missed, is NOT credited when the truck crosses the start line, and the lap
  counter stays put.
- Checkpoint positions are on Flat road and the gate is wider than the road.

Report the lap time and score of the autopilot lap before and after your change
so it is clear nothing regressed.

PROMPT 2 OF 8 - TRUCK SETUP ON THE NUMBER KEYS
================================================================================
Model:   Opus 5
Why:     Smallest change in the plan, mechanical, hard to get wrong.
Depends: nothing
Size:    ~100 new lines

>>> COPY FROM HERE >>>
Let the player change how the truck handles in corners, using the number keys.

Design decision already made, implement it as described: this is a trade-off,
not a difficulty slider. Five tyre setups on keys 1 to 5, running from soft to
hard. Softer setups have more grip and a lower top speed; harder setups have
less grip and a higher top speed. Setup 3 is the current car and is the default.
Clamp grip to the range 0.6 to 1.25. Above roughly 1.25 the truck tips instead
of gripping, so do not let the player select that.

Work:

1. Truck: add a small Setup struct (grip and top speed, and anything else you
   judge belongs) and a setter for it. The current values are m_grip 1.10 and
   m_topSpeed 40.0; keep those as setup 3.

2. Game: hold the current setup, expose it, and keep it across reset() so the
   player does not lose their choice when restarting. Do not reset it on
   recover() either.

3. wasm: export a function to select the setup by index.

4. docs/monster.js: bind Digit1 to Digit5, and show the current setup in the HUD
   (name and a short hint, for example "TYRES 2 SOFT  grip 1.18 / top 36").
   Update the on-screen help line.

5. The HUD string format changes, so update tests/smoke.mjs to match.

Tests to add:
- A softer setup measurably reduces sideslip in a sustained full-lock corner
  compared with a harder one. Run this on empty ground well clear of the
  circuit: a turn circle started near the track sweeps back over the wreck at
  x = 35 and the collision, not the tyres, then decides the result.
- A harder setup reaches a higher speed on the straight.
- Out-of-range setup indices are rejected or clamped, not silently accepted.
- No setup allows a sustained full-lock corner to tip the truck (up().y stays
  above 0.9).

PROMPT 5 OF 8 - OPPONENTS
================================================================================
Model:   Fable 5.2

         trucks is where this project could quietly stop being small, and that
         judgement call is worth the stronger model.
Depends: prompt 3 (required), prompts 1 and 4 (strongly preferred)
Size:    ~600-800 new lines

>>> COPY FROM HERE >>>
Add three computer-driven opponents and turn Monster into a three-lap race.

Starting point: tests/Autopilot.* is already a working driver. It is 89 lines,
follows the centreline with a look-ahead target, brakes for bends, holds the
wheels straight through the loop, and completes a clean lap. Promote it to
src/ as the opponent driver rather than writing a new one.

Work:

1. Move Autopilot into src/ as the driver for a Racer. Give it a parameter set
   (look-ahead distance, steering gain, corner speed, braking deceleration,
   planning distance, and a throttle cap) so difficulty can be varied later.
   For this step, give the three opponents visibly different but roughly
   plausible parameters; prompt 6 tunes them properly.

2. Four racers: the player plus three opponents, each a different colour, lined
   up on a staggered grid behind the start line. The opponents must pass the
   same checkpoints in the same order as the player to be credited a lap.

3. Truck-to-truck contact. Design decision already made, implement this and not
   something more ambitious: approximate each truck with a few spheres along its
   body, and when spheres of two trucks overlap, apply equal and opposite
   push-apart forces (a spring along the contact normal plus damping along the
   relative velocity) through the existing force accumulation in Truck::step.
   Do not build a general contact solver or an impulse-based collision system.
   Contact should feel like bumping, and must never launch a truck into the air
   or push one through the road.

4. Race state: three laps, finish order, and the race ending when the player
   finishes. Track each racer's position in the field. R restarts the whole
   race, opponents included, from the grid.

5. HUD: the player's position in the field (for example "P2/4"), lap "2/3", and
   the result when the race ends.

Watch out for:
- Recovery and the wrecked state are per-racer now. An opponent that rolls over
  must recover the same way the player does, or it will block the circuit.
- The ray-cast collision world only contains static geometry. Trucks are not in
  it, which is why contact is handled separately.
- Performance: four trucks at 240 Hz is about 40,000 ray casts per second.
  Measure the frame time and report it; if the fixed step becomes the
  bottleneck, say so rather than silently lowering it.

Tests to add:
- All four racers complete three laps within a sensible time window and none
  falls through the world or ends the race stuck.
- Every credited lap passed all five checkpoints.
- Two trucks driven into each other separate, neither leaves the ground, and
  neither ends up below the road surface.
- Resetting restores all four racers to the grid with zero laps.

Run the circuit through a mountain ridge twice, once from the green side into
the desert and once back, with a tunnel at each crossing.

Two things make this easier than it sounds, use both:
- Collision is ray casts against triangles, so a tunnel ceiling needs no special
  case. The old height map could not have represented one.
- Terrain::buildRoad already switches on PathPoint::Kind to add walls under
  embankments and leave the span open under the bridge. A Tunnel kind that adds
  side walls and a roof is a natural extension of the same code.

Do not model a solid mountain with a bore drilled through it. Build the ridge as
two mountain masses with a gap between them, put a portal facade at each end of
the gap, and run an enclosed road section between them. From inside the truck it
is indistinguishable, and it is a fraction of the work.

Work:

1. Add PathPoint::Kind::Tunnel and place two tunnel sections in the Track
   layout, positioned so the ridge separates the green and desert halves from
   prompt 7. Keep the existing loop and bridge intact and check the circuit
   still closes.

2. Build the tunnel: side walls, a ceiling high enough to drive under but low
   enough to feel enclosed, and portal faces at each end. Darken the baked
   vertex colours inside so it reads as a tunnel rather than a corridor.

3. Put a checkpoint on each side of each tunnel. Re-space the existing
   checkpoints if needed.

4. Build the ridge itself from the existing mountain geometry, scaled and placed
   so the portals sit in its flank.

Tests to add:
- A ray cast straight up from inside the tunnel hits the ceiling, and one from
  just outside the portal does not.
- A truck driven at full speed through the tunnel cannot leave through the roof.
- The autopilot still completes a clean lap, and the circuit still closes to
  within a millimetre.
- The loop and bridge still work as before.

Report the new lap distance and autopilot lap time, and include screenshots of
both portals and the inside of a tunnel.

NOTES

If a prompt produces too large a change to review comfortably, the natural
split points are:

  Prompt 1  gate geometry and digits, then the lap rule
  Prompt 5  the driver and four racers first, contact between trucks second
  Prompt 8  the tunnel geometry first, the ridge and checkpoints second

Prompt 3 is the one not to skip or merge into prompt 5. Doing the refactor on
its own, with the whole test suite green and the autopilot lap time unchanged,
is what keeps the opponents diff small enough to read.

Expected growth: src goes from about 2,650 lines to roughly 4,200. The frame
goes from about 31,000 vertices to about 48,000, which is still nothing for any
GPU of the last fifteen years. The cost that actually scales is the per-frame
mesh rebuild in C++, which is what prompt 4 removes.
